FormGlut per-form settings plan

Today every setting is global; the only per-form options are the fields and the submit button. This is the list of form-level settings to add to the free plugin, how to store them, and the order to build them. Evidence comes from the 7 full form plugins installed next to FormGlut.

How to build it

The forms table already has an unused appearance_settings column and the editor already has a right-hand panel with tabs, so this fits the current architecture.

Storage and flow
  1. Add a settings longtext column to the forms table (dbDelta migration in the activator; keep appearance_settings for style values).
  2. Save it with the form: send settings in the create/update ajax call and sanitise it with a whitelist in a new sanitize_form_settings() next to sanitize_form_fields().
  3. Read it with a helper FormGlut_Form::get_setting( $form, 'confirmation.type' ) that merges: built-in default ← global setting ← form setting.
  4. Enforce on the server first (shortcode render for closed/login messages, submit_form() for limits, spam, storage, email); the browser only receives what it needs (confirmation, button text).
  5. Editor: add a fourth tab Form Settings next to Add Fields / Field Options / Style Options, or a modal from the header. Sub-tabs = the tabs below.

Build order

Phase 1: foundation

Storage, the Form Settings tab, then the settings that change what users see: confirmation (message / redirect / after-submit), per-form notification (recipients, from, subject, message with smart tags), title toggle, form class, per-form AJAX and “sending…” text.

Phase 2: control and protection

Require login, entry limit, schedule, auto-responder, per-form honeypot / store-entries / store-IP overrides, scroll-to-message, error and asterisk placement.

Phase 3: polish

Akismet, keyword filter, one-per-user, retention, minimum fill time, custom CSS, form colours (largest item), multi-step labels once the step field exists, standalone form page.

Keep for Pro

Conditional notifications / confirmations, multiple notifications, style presets, save & resume, webhooks and integrations, payment settings. Competitors ship the simple versions of the settings above in their free plugins.

Method and limits
  • Each setting was searched by name in the source of Fluent Forms, WPForms Lite, Ninja Forms, Forminator, Formidable, SureForms and MetForm (Form Maker, NEX-Forms, Gutena and Gutenverse were left out because they keep form settings in ways that can't be matched by name). “Seen in” means that plugin's code contains that setting name.
  • Names are matched as text, so a few short names (for example email, title, views) can match unrelated code. Treat the chips as a hint and confirm in the plugin's own form settings screen before copying the behaviour.
  • Left out on purpose because FormGlut already has them per field (Field Options / Style Options) or in the submit button panel: label position, help message position, submit button text, button alignment / colours, and autocomplete.
  • “FormGlut today” was checked in the FormGlut code. Phase and effort (S / M / L) are my estimates for this codebase.
